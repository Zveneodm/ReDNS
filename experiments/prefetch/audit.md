# 预取实现审查与上次实验拆解

审查对象是提交 `117da42` 的首次实现和 `res/prefetch/comparison.json` 指向的完整实验。本文件中的性能数值全部来自该历史实验，不是修复后的新正式实验。原始结果、配置、指纹和第一次的报告保持保留。

结论：3.354% 的均值改善不能被解释成 Forestall 的收益上限。实现里有需要修正的时序、统计问题，更大的已知限制是非常紧的任务预算和缺乏收益区分的排序。数据也不支持把收益小简单归因于 client 容量不足或笼统的“缓存污染”。

## 代码正确性与框架接口

检查了预取需求采集、跨进程消息路由、manager 域名分片、记录 TTL、普通缓存回填、预热/正式阶段归属，以及前后台回源统计。上次三组的全部原始结果重新通过流量守恒校验；重新生成完整请求序列和权威 TTL 表，两个 SHA-256 指纹与保存结果一致，每组正式请求数为 8,998,486。

发现并修复以下三个问题；新增五个回归测试，在旧代码上有四个失败，在修复后全部通过：

1. **建议周期漂移。** 原代码设置 `next = 实际运行时刻 + A`。一次在 5.002 秒处理完报告，下一次在 10.001 秒处理时就会跳过，而不是按 10 秒边界执行。修复为对齐固定模拟时刻 A、2A、3A；来晚的报告触发最近边界，不连续补跑历史周期。上次正式阶段两个 manager 分片合计只执行 217 次，名义周期对应约 240 次，说明漂移确实减少了调度机会。
2. **跳过任务也消耗无效建议额度。** 原代码在派发时立即 `mark_advised`，即使 forwarder 随后因为容量、繁忙或运行结束而跳过，也可能触发 epsilon/zeta 的处罚。修复为实际回源完成后才记为一次建议。原实验 epsilon/zeta 都不限制，因此这个问题不能拿来解释上次主要的性能差异，但会破坏其他合法参数组合。
3. **跨上报周期迟到的响应漏计间隔。** 原代码只在一个批次内部排序；先收到 0.95 秒请求的回复、后一个批次才收到 0.90 秒请求的回复时，后者的到达样本被忽略。修复后 forwarder 上报最早未完成请求的时间界限，manager 暂存尚不能确定顺序的事件，只按所有成员已越过的安全时间界限合并；跟踪器遇到乱序输入直接报错，避免静默改变统计。

完整测试套件最终 **158 项通过**，包括真实多进程、多个 manager 域名分片、多个集群、阶段切换和流量守恒。它验证修复与框架接口，不意味着已经证明策略最优，也不意味着逐行复现了论文算法。测试输出见 `audit_tests.log`；旧代码上的失败复现见 `audit_before_fix.log`。

## 任务预算是已证实的主要限制

| 调度阶段 | 次数 |
| --- | ---: |
| 候选建议 | 1,142,854 |
| 派发任务 | 86,800 |
| 实际回源并存入 | 83,539 |
| 执行时跳过 | 3,261 |
| 在预取落点被使用的记录 | 33,928 |

只有 **7.595%** 的候选建议被派发，另有 1,056,054 次候选建议未派发。候选次数会重复包含同一域名，不能当成独立域名数，也不能把全部未派发都归为同一种原因。

当前每 forwarder 每轮额度为 8，两个 manager 分片各拿 4，集群有 100 个 forwarder，因此每个分片一轮最多派发 400 个。**86,800 = 217 × 400**：每轮都把额度用满，配额确实构成瓶颈。其名义上限约为 160 次预取/模拟秒，实际仅约 139 次/秒，而候选建议约 1,905 次/秒。

更具体地，100 个 forwarder 在上次正式阶段收到的任务数**全部恰好为 868**，实际开始 814–858 次，跳过 10–54 次。因此所谓“优先低负载”主要改变了派发顺序和域名落点，没有在任务数量上把更多工作转给空闲节点：每个节点最终都被派满自己的额度。

当前排序还会把过去的 deadline 压成 `now`，再按 `(deadline, domain_id)` 排序。当大量候选都已经到期时，域名整数 ID 参与了限额下的选择，未按预计能节省的前台回源数打破平局。可控示例中，平均请求间隔 4 秒和 0.4 秒的候选都变成同一个 deadline，较冷但编号小的域名排在前面。该示例证明策略没有有效区分这些候选；原实验没有保存任务级清单，无法量化 ID 偏好实际损失了多少收益。

## 收益有多少被其他请求的退化抵消

对同一计划请求逐条比较两份延迟数组：

| 同一请求的结果变化 | 次数 |
| --- | ---: |
| 原 ReDNS 回源，预取版缓存命中 | 70,815 |
| 原 ReDNS 缓存命中，预取版回源 | 33,899 |
| 净减少前台回源 | 36,916 |

净变化正好匹配 `1,020,304 - 983,388 = 36,916`。约 47.9% 的回源改善次数被反向变化抵消。这里描述的是两次运行的配对结果，**不是**证明那 33,899 次都由预取缓存污染造成；TTL 刷新相位、查询候选排序和实际进程调度都可能改变哪些具体请求命中。

单次预取落点使用比例为 `33,928 / 83,539 = 40.61%`，不能把其余 59.39% 直接标成浪费：预热/正式接受阶段、转存后的后续使用以及结束时仍然有效的记录都影响这个计数。原始结果缺少每个预取任务的入缓存、逐出、首次使用轨迹，无法进一步精确归因。

## 请求与 TTL 决定哪些回源有机会被预测

| 原 ReDNS 正式回源时的请求历史，包含预热历史 | 次数 | 占原回源 |
| --- | ---: | ---: |
| 全实验第一次出现该域名 | 357,125 | 35.00% |
| 此前只有一次该域名请求 | 126,710 | 12.42% |
| 此前至少两次该域名请求 | 536,469 | 52.58% |

当前方法至少需要一个请求间隔，即两次已观察请求，才能提前建议。首次域名没有可用预测历史；第二类在请求发生前也没有满足该门槛的历史间隔。上述统计使用所有 client 请求，forwarder 仅看得到 client 未命中后上交的请求，因此它只是更宽松的机会范围。它不代表 3.354% 是理论上限，仍有很大的可优化空间。

| TTL（秒） | 原 ReDNS 回源 | 预取版前台回源 | 净减少 |
| --- | ---: | ---: | ---: |
| 20 | 124,075 | 117,905 | 6,170 |
| 60 | 590,414 | 562,479 | 27,935 |
| 300 | 162,536 | 159,725 | 2,811 |
| 900 及以上 | 143,279 | 143,279 | 0 |

**92.54% 的累计延迟净收益来自 TTL=20/60 秒的请求。** TTL≥900 秒超过整个 800 秒运行窗口，这些域名的全部回源也确实是首次出现；当前重复访问预测不能改善它们。长 TTL 请求还有轻微的缓存查询路径成本增加。

原 ReDNS 的 client 容量淘汰为 0；forwarder 虽然发生 1,564,840 次 LRU 淘汰，但因为直属 client 已有副本，这些淘汰全部跳过了额外转存。不能把这些 forwarder 淘汰直接等同于集群丢失记录。保守时间界限检查还发现：482,262 次回源存在更早的正式回源可供核对，其中 464,545 次（96.33%）可以确定前一次答案已经过期；没有找到能够保守证明“前一次答案仍有效且已完成，本次却再次回源”的样本。其余样本及缺少正式前驱的样本没有被强行分类。

## 框架评估的是累计 RTT，不是真实网络排队

框架将 110 ms 权威 RTT 加到延迟账面值，但不会真的等待 110 ms；预取的在途数随真实 IPC 回复结束。因此它能比较缓存路径所需的配置 RTT，却不能准确验证“负载更低的 forwarder 降低网络排队”这类收益。100 个逻辑 forwarder 也只由 4 个进程承载，节点负载并不等于 CPU 分片负载。

真实进程/IPC 平均耗时从 0.755 ms 增至 1.255 ms。按计划到达时间在每个模拟秒内的位置分组，秒开始后 0–100 ms 的请求平均耗时从 **0.974 ms 增至 4.571 ms**，100–200 ms 从 **0.605 ms 增至 2.306 ms**；其余时段差异小得多。这与整秒批量上报、合并统计和集中调度的代码路径相符，但没有消融试验证明每个因素的独立贡献。

所以，13.056→12.618 ms 是累计配置 RTT 降低，不能当成真实部署端到端延迟降低。增加预算之前还需要同时控制后台流量和批处理开销。

## 后续策略优先级

先保留已修复的时序与统计问题；然后将“每轮任务预算”和“同时在途上限”分成独立参数，用预计收益区分 deadline 相同的候选，并让每个节点的预算能够随负载变化。下一轮实验应分别比较仅负载排序、仅预取、两者结合，配额按多个水平扫描；新增任务级入缓存/逐出/首次使用和拒绝原因统计。这样才能判断提高覆盖率后收益是否值得额外流量。

当前实现仍包含历史统计方式、gamma 判定和 TTL 门槛等工程选择，并非 [Forestall 论文](https://doi.org/10.1109/TNSM.2026.3704549) Algorithm 2 的逐行实现。一个可控示例还证明：没有缓存副本时，旧的观测 TTL 仍可阻止预取；但本次真实数据不能把它认定为主要损失原因。该例和排序/时钟例见 `audit_probes.json`。

可复跑的数据拆解脚本为 `audit_saved.py`，完整数值为 `audit_saved.json`；诊断示例脚本为 `audit_probes.py`。修复后的短多集群兼容性对照使用 `audit_validation_config.json`，结果摘要见 `audit_validation.json`。短对照与回归测试用于验证兼容性；没有重新运行 200 秒预热、600 秒正式窗口的完整性能对照，不能把历史 3.354% 当成修复后的性能数值。
