# 标准配置下的预取消融结果

在本轮标准配置和集群预取策略下，加入 ReDNS 协作使平均配置 RTT 从 **19.335367 ms 降至 10.899552 ms（降低 43.63%）**，含预取的总权威查询从 **1,911,842 降至 1,230,455（降低 35.64%）**。这支持 ReDNS 在当前预取方案上具有明显的额外价值。

两组各完成 **8,998,486 次正式请求**，使用相同 seed、计划请求序列、TTL 表、容量、替换策略、CPU 与预取参数。均为预热 200 秒、正式 600 秒、time_scale=2，首次完整对照即通过，没有调整标准配置或拼接历史结果。运行结束时 `src/`、`sim/` 的源码指纹与实验记录一致；项目根目录 `config.json` 与实验快照逐字节一致。196 项回归检查通过。

## 效果和权威流量

| 指标 | baseline-prefetch | ReDNS-prefetch | 变化 |
| --- | ---: | ---: | ---: |
| 平均前台配置 RTT（ms） | 19.335367 | 10.899552 | 降低 43.63% |
| p95 / p99 配置 RTT（ms） | 111 / 111 | 112 / 112 | 均增加 1 ms |
| 前台权威查询 | 1,558,370 | 838,241 | 减少 46.21% |
| 后台预取权威查询 | 353,472 | 392,214 | 增加 10.96% |
| 总权威查询 | 1,911,842 | 1,230,455 | 减少 35.64% |
| 每用户请求的总权威查询 | 0.212463 | 0.136740 | 减少 35.64% |
| 前台回源请求比例 | 17.3181% | 9.3154% | 降低 8.0028 个百分点 |
| 正式存入的预取记录 | 353,472 | 392,214 | 增加 38,742 |
| 至少使用一次的预取记录 | 1,680 | 159,054 | 增加 157,374 |
| 预取记录使用比例 | 0.4753% | 40.5529% | 增加 40.0776 个百分点，约 85.32 倍 |

ReDNS 多做了 38,742 次后台预取，但减少了 720,129 次前台回源，净少 681,387 次权威查询。因此，平均链路成本的改善在本轮也伴随总权威流量下降。不同模型的前台需求、缓存历史和建议列表会不同，相同预算比例不保证相同预取次数。

## 为什么 ReDNS 有帮助

两组都使用集群级热度和低负载落点。baseline-prefetch 只能让落点 forwarder 及其正常请求回填后的 client 使用答案；集群里其他 forwarder 无法发现这个预取副本。本轮它的 353,472 条正式预取记录中只有 1,680 条在落点至少使用一次。这与低负载派发缺少域名访问亲和性、又缺乏协作取回的解释一致，但未逐任务重放验证，不能把全部未使用原因都归为放置问题。这里的使用比例不是预测准确率，观察末尾未用记录也不能全部算作浪费。

ReDNS-prefetch 通过区域目录让其他 forwarder 定位这些答案，也能从 client 副本取回。本轮实际发生：

- 187,332 次直属 client 探测命中。
- 606,429 次集群命中，其中 249,057 次来自邻居 forwarder 缓存，357,372 次来自邻居 client。
- 544,738 次成功反向查询；该逻辑计数与上面的物理命中存在重叠，不能相加。
- 298,289 条记录被转存到 client；正式接收组中 58,915 条转存记录至少使用一次。

ReDNS 的 client 本地命中率为 70.897%，低于 baseline-prefetch 的 71.475%；forwarder 本地命中率也略低（37.647% 对 39.287%）。因此，收益主要体现在本地 miss 后还能通过协作取回答案，而不能解释为普通本地缓存命中率普遍上升。

预取使用统计由存入阶段归属，覆盖该落点记录至少一次实际使用；逐出、转存后的使用另记为转存指标，不补记到原预取记录。未保存逐请求的完整预取因果链，因此不能把所有协作命中都归为预取命中，也不能把平均时延的全部改善归因于预取副本共享。两组比较衡量的是整个 ReDNS 协作机制在相同预取策略下的价值。

## 实现开销和慢尾

| 指标 | baseline-prefetch | ReDNS-prefetch |
| --- | ---: | ---: |
| 实际前台进程 / IPC 平均耗时（ms） | 0.152179 | 5.543935 |
| 实际前台进程 / IPC p95（ms） | 0.343933 | 1.741230 |
| 实际前台进程 / IPC p99（ms） | 0.820484 | 208.058767 |
| 全窗口 IPC 消息数（含预热） | 14,056,388 | 29,337,590 |
| 平均到达滞后（模拟秒，含预热） | 0.000579 | 0.002060 |
| 窗口结束后的排空时间（模拟秒） | 0.009210 | 0.011383 |

当前 Python 多进程实现的平均实际耗时增加约 36.43 倍，IPC 消息增加约 2.09 倍，实际慢尾明显增大。目录通知、manager 定位和协作 RPC 都增加工作；未做 CPU、GC、队列各部分的剖析，不能仅凭这些计数精确分摊耗时。此轮不支持“所有时延指标都改善”的结论。

主时延是模拟器累加的配置 RTT，实际 IPC 耗时另列，两者没有相加。后台预取不直接计入主时延，但可以通过资源竞争影响实际 IPC 耗时。p95 配置 RTT 从 111 ms 增为 112 ms，也表明本轮改善集中在平均链路成本与回源量，尾部请求仍走权威路径并可能多一次 manager 定位。

两组均存在短暂到达滞后；最大单请求滞后分别约 0.660 和 0.635 模拟秒。最长超限窗口连续数均为 2，低于配置的 3；全局均值和排空时间也通过标准门限。完整时序窗口保留在原始结果中，验证摘要没有把“通过门限”解释为“完全没有抖动”。

## 结论范围和复现

这轮结果说明：**在当前集中热度、低负载分散派发的预取策略下，ReDNS 的副本发现和协作取回能提高预取记录的实际使用比例，并降低平均配置 RTT 与总回源成本。** baseline 仍可通过按独立 resolver 的本地热度与访问亲和性设计其他预取策略；本实验没有评估那些方案。

这也是单 seed 的一次完整运行，未计算重复实验置信区间。仅凭这两组，不能单独估计“预取本身的边际收益是否因 ReDNS 而增大”；该交互效应需要同版本、同条件的四组实验。这里没有用旧版本无预取结果拼成四组。
